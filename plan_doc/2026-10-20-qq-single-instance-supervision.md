## 已证实的启动缺陷

核验时间：2026-10-20 12:17:39（北京时间）。

1. 存在两个真正的 QQ 主进程，不是 zygote/renderer 子进程：
   - PID 1623734：带 `--relaunch`，进程组 1623734，stdout/stderr 指向 `/dev/null`。
   - PID 1623748：由 Supervisor 管理，进程组 1623748，stdout/stderr 指向 Supervisor 管道。
2. 每个进程各有一个独立、可见的顶层 QQ 窗口。窗口均为 320×460，位置相同，因而在桌面上重叠。
3. 10 月 12 日历史记录（北京时间）：
   - `/proc` 启动时钟显示 `--relaunch` 主进程先出现；该启动时间由内核时钟换算，亚秒精度不作为独立结论依据。
   - 14:43:44.861：Supervisor 记录 `exited: qq (exit status 1; not expected)`。
   - 14:43:45.527：Supervisor 记录 `spawned: 'qq' with pid 1623748`。
   - 14:43:46 / 14:43:48：两个进程分别被 Hook 连接。
4. Supervisor 的 `autorestart=true`；`stopasgroup=true`、`killasgroup=true` 已经存在。
5. 容器本身没有在该事件中重启，RestartCount=0。

因此已锁定：QQ 的 relaunch 路径留下另一份主进程，原受管进程退出后 Supervisor 又按既有规则启动一份，两个独立主进程同时存活。现有部署没有协调该进程交接，也没有阻止重复拉起。

尚未确定：最初是什么动作或异常触发 QQ relaunch。不能据此认定账号被盗、自动更新故障或某个用户操作。

## 必须纠正的判断

- Agent 的 142 个受控源码全部正确，只能证明应用文件完整，不能证明整套 QQ/SnowLuma 部署运行合格。
- Hook loaded/connected 不等于 QQ 已登录，也不等于单实例约束满足。
- 简单添加 stopasgroup/killasgroup 无效：它们已经启用；重启受管进程不会自然接管另一进程组中的遗留 QQ。
- 仅将 autorestart 改为 unexpected 也不能解决本例：旧进程实际退出码是 1，本来就属于 unexpected。
- 直接关掉 autorestart 会丢失崩溃恢复，并可能让 relaunch 后的 QQ 脱离监管，不作为持久修复。
- 删除 QQ 的锁文件、登录数据，或换新数据目录不属于本方案。

## 持久修复方向

在本项目控制的部署层增加 QQ 单实例监管入口，而不是只临时杀掉一个 PID：

1. Supervisor 监管稳定的启动/交接进程，由它启动、监视并识别实际 QQ 主进程。
2. 启动前检查该容器、同一服务 UID、同一 QQ 可执行文件与同一应用数据上下文中的主进程：
   - 无实例：启动一份。
   - 有且仅有一份可确认归属的遗留实例：接管监视，不额外启动。
   - 多实例或归属不清：失败闭合并报告，不继续复制实例、不自动任选账号或杀未知进程。
3. 原 QQ 退出时先识别其 relaunch 交接；已有合格的新 QQ 就接管，不能同时再 spawn 一份。
4. 停止监管入口时，对已确认归属的当前 QQ 及交接过程做有界收尾，不把进程组之外的遗留实例静默留下。
5. 启动资产通过项目的部署模板和持久只读挂载交付。保留镜像中其他程序与安全参数，仅变更 QQ 监管链。
6. 同步现有部署归属/挂载校验与更新路径，确保重跑部署不会擦掉修复，额外挂载不会绕过受管安装校验。

### 已核实的实现契约

- 镜像自带 `/usr/bin/python3`，采用 Python 标准库单实例监管，不新增宿主 Python 或 npm 依赖。
- 复用原 Supervisor 的 include 接口：只读挂载 `qq-supervisor.conf` 到 `/etc/supervisor/conf.d/qq-agent-single-instance.conf`，只覆盖 `[program:qq]` 的 command 和 stopwaitsecs；不覆盖整份 Supervisor 配置、不改 `/root/start.sh`。
- 已用当前镜像的实际 Supervisor 解析器在临时目录验证：覆盖后 QQ 仍为 uid1000、HOME=/app、原进程组停止参数继承，SnowLuma 命令与配置保持原样；未启动任何测试 QQ。
- 监管程序只读挂载到 `/opt/qq-agent/qq-supervisor.py`；两个宿主资产及哈希清单位于 `snowluma/qq-supervision/`。部署辅助模块负责安装与只读校验，归属检查兼容旧三挂载和新五挂载，但拒绝半套资产、额外挂载或非只读代码挂载。
- 固定 `SNOWLUMA_EXTRA_QQ_HOMES` 为空，禁止该单账号栈生成额外 QQ 服务。
- 通过 flock 保证一份监管者，排除 `--type=` Chromium 子进程；运行中允许有界 relaunch 交接，无交接的退出交回 Supervisor 处理，多实例启动失败闭合。
- 真实非 root 权限核验发现 Hook 保护的 QQ 禁止同 UID 读取 `/proc/PID/exe` 和 environ，但公开 cmdline、UID、comm、启动标识可读，信号权限也正常。为保持非 root 且不新增 ptrace 能力，生产配置显式使用 `--container-scope`：只允许固定 `/opt/QQ/qq`、HOME=/app 且 PID1 为 supervisord 的专用容器；以 UID、comm、规范 argv0 与 PID 启动标识识别受保护 QQ，拒绝未知程序或可读的额外 HOME。该模式的 HOME 边界来自专用单账号容器配置，不冒充读取到了受保护 environ。通用/共享宿主模式仍要求真实 exe/HOME 可核验，不允许该兼容策略跨到宿主进程。
- 停止只清理已验证属于此 QQ 上下文的进程，并检查 PID 启动标识，避免误杀复用 PID；不删 QQ 锁文件或用户数据。
