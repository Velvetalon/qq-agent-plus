## 1. 产品目标：像群友，而不是处理消息的助手

机器人应当理解眼前的人、对话指向和话题进展，有稳定但不僵硬的性格，能够接话、开玩笑、认真回答、保留自己的看法，也能自然旁听和结束。主动性来自具体兴趣或新的可表达内容，而不是定时器要求它出声。

“拟人”不等于假扮真人、不等于每句都带人设、不等于故意乱答，也不等于把短句、毒舌或表情当成配额。允许普通的一句话、一次认真长答、单张表情和完整沉默。是否自然主要由时机、对象、相关性、表达目的和长期一致性决定。

成功不以“零发言、零记忆、零主动”为标准，也不以“消息更多、每轮都调用工具”为标准。工程护栏只保证边界，不能替代模型的语言和社交判断；效果评价必须保留代表性对话的人工判断。

## 2. 当前问题与重构边界

| 已确认问题 | 架构原因 | 目标改变 |
| --- | --- | --- |
| 回应像逐条点评、套用固定结构 | 一个工具循环同时承担参与判断、措辞、记忆和调度；平台反复要求短句补话 | 明确参与决策与表达职责，删除平台级表现配方 |
| 插话、指向不清、接旧话题 | 群级生命周期不等于真实话题；最新一批消息与旧模型上下文容易混合 | 持久的轻量多话题现场、目标与材料来源 |
| 无人回应后继续催话 | 发言本身触发 follow-up，冷场被当成新任务 | 统一主动意图和机会调度，不因无人回应自动续话 |
| 生成期间话题变化仍发送 | 输入快照和实际投递之间缺少有效性契约 | 相关性驱动的失效检查、有限重规划 |
| profile 清空后旧脚本仍出现 | Notebook、交接、向量和模型续接各自注入，没有统一记忆使用边界 | 写入、检索、工具读取、反思、派生上下文共享策略 |
| 正常学习被挡、沉默反而绕过 | 新旧事件协议混用；trait 门槛控制整个反思作业；三会话与单会话窗口矛盾 | 宿主 v3 事件、经历与偏好两条处理路径 |

截至 2026-10-13 的只读评估显示：更新后 57 个群聊运行中有 40 个仍召回旧 result=120 内容，34 个 trait 门禁拒绝都只有一个有效会话，另有 7 条无新输入发言。该快照是需求依据，不作为以后实时状态；不能据此推断上线时仍有相同条数。

保留 OneBot 接入、消息存档与租约、PluginManager、Sender/Outbox、鉴权、未知投递保护、SQLite 和现有控制台。重构 Orchestrator 内的聊天内核，不建设新微服务、通用工作流平台或第二套消息投递系统。

新内核使用 conversation.mode=social。legacy/threaded/lifecycle 保留为明确回退选项；既有安装不自动切换。开发、采用新模式、上线、数据清理、解除禁言是不同操作，不能互相暗含授权。

## 3. 总体结构与模块所有权

~~~text
真实消息 / 已授权外部观察 / 到期意图
                    |
       Ingress + Message Store / Lease
                    |
       Scene：人物、指向、话题、互动片段
                    |
       Opportunity：权限、预算、参与机会
                    |
       Planner：回复谁、为什么说、是否等
                    |
       Context Builder：按目标重新选材料
                    |
       Replyer：生成一个自然的交流回合
                    |
       Delivery Guard：此刻还值得发吗
                    |
       Sender / Outbox：实际投递与结果
                    |
       Completion v3：宿主确认的结果
              /                    \
      Episodic Writer        Preference Candidates
      一次有意义经历          多来源、反证、采用
~~~

| 组件 | 所有权与职责 | 禁止承担 |
| --- | --- | --- |
| Orchestrator | 批次、Run 预算、取消、生命周期接线、ack | 在一个大函数里实现人格学习或第二套发送 |
| SceneStore | 账号/会话内的话题、互动、消息关系与场景版本 | 让模型生成账号、真实消息 ID、投递事实 |
| OpportunityPolicy | 硬权限、去重、并发、沉默/参与软信号 | 以达到发言数量为目标 |
| Planner | 读现场、查必要资料、选择意图和时机 | 外部发送、直接改设置或无限规划 |
| Replyer | 按目标自然表达，必要时继续只读获取材料 | 自行创建定时循环、决定自己的权限 |
| IntentScheduler | 有来源的待表达事项、期限、机会、恢复 | 保存聊天全文为脚本、替代投递重试 |
| MemoryService | 笔记类型、范围、版本、召回和撤销 | 把相似文本自动升级为行动权限 |
| Reflection | 提议经历或偏好，返回可审计来源 | 根据自己的历史回复证明用户认可 |
| Delivery Guard + Sender | 发言有效性 + 可靠外发 | 未知结果自动重发 |

模块放在同一 Node 进程中，复用已有 SQLite；拆职责不等于拆部署，也不要求多个常驻 Agent 或多家模型。

## 4. 统一身份和事件协议

### 4.1 身份与 ID

- accountId、chatKey 由宿主当前账号和消息来源绑定，不从模型参数读取。
- messageId 是存档 ID，platformMessageId 是 QQ 消息 ID，必须显式映射，禁止混用碰巧相同的数字。
- topicId 表示话题；interactionId 表示一次独立互动片段；sessionId/runId 表示一次执行。三者不能混为一谈。
- 一次互动被防抖拆成多批、工具循环重跑或重试，不能因此变成三次独立人类证据。
- 引用、转发、检索摘要携带 originalSourceIds；重复引用原文不会增加独立证据数量。

### 4.2 ConversationEvent v3

| 字段 | 含义 | 谁能确认 |
| --- | --- | --- |
| schemaVersion、eventId、occurredAt | 协议、幂等身份、实际时间 | 宿主 |
| accountId、chatKey、messageId、platformMessageId | 作用域和原始记录 | 宿主 |
| kind | human_message、bot_delivery、initiative_due、external_observation、operator_action | 宿主 |
| role | user、assistant、tool、system；不猜缺失角色 | 宿主 |
| triggerKind、originalSourceIds、interactionId、topicId | 因果来源和对话归属 | 宿主为主，语义归属可接受经校验的提议 |
| deliveryState | not_attempted、sent、failed、unknown、partial | Sender/Outbox |
| explicitFeedback | 谁对哪个行为提出何种反馈的来源引用；可为空 | 有真实来源的结构化记录，不由情绪词猜测 |
| interpretation | 模型的短摘要/解释，不是系统事实 | 模型，明确标注 |

旧 v2 事件继续可读和审计，不允许因缺少新字段退回宽松 trait 采用路径。消息是否发出和用户是否认可必须分开；文本中的错误码不得被当成宿主实时故障。

## 5. 对话现场：轻量、多话题、可纠正

Scene 保存有界活跃话题、参与者、机器人参与状态和近期真实事件。话题状态为 active/listening/closed；历史记录不因话题关闭而删除。

归属顺序：先使用原生引用和明确目标，其次使用短期参与者连续性；含混消息由 Planner 建议归属或创建新话题。模型建议只能引用当前可见的真实消息，并在场景版本校验后采用。短期同一个人发言不必属于同一话题，不能用用户 ID 直接当 topicId。

每个话题保存 topicVersion、lastHumanEvent、lastBotEvent、被回答目标、未决事项及当前轮材料上界。场景发生不相关变动不使整个群的所有草稿失效。

interactionId 以话题中的因果连续性为依据，由宿主创建：引用续接、同一请求补充、工具结果补充、发送重试属于同一次；话题结束或足够时间后新的独立互动才开启新片段。时间间隔是辅助，不是多刷几次就能刷满学习门槛。

容量达到上限时优先关闭/压缩不活跃话题，但保留消息存档、审计和待办来源。不能为了腾位置删除仍被待办、未知投递或候选证据引用的原始记录。

## 6. 参与决策：硬约束少，软判断交给模型

### 6.1 硬门槛

运行权限、白名单、禁言/观察模式、当前时间控制、并发上限、重复事件、未知外发状态、明确管理员暂停。这些在模型调用前检查。

### 6.2 软信号

是否直接找它、是否回答它、是否只是别人之间的引用；人是否还没说完；话题是否已有足够答案；机器人能否提供新信息、情绪回应、幽默或立场；最近自身发言占比、未获回应的主动次数、重复意图和话题兴趣。

不要求硬编码复杂评分公式，也不以消息占比作为唯一阻断条件。低/中/高参与度影响倾向和预算，不覆盖明确邀请，不制造最低发言配额。只读模型不可用时记录原因并等新证据，不用随机套话兜底。

### 6.3 Planner 输入与输出

输入：当前人格摘要与附加规则、最近真实对话、场景快照、当前触发、新旧消息边界、可选待办、少量相关经历摘要。读取目标明确的图片或网页可以使用已有只读工具，结果保留来源。Planner 不获得发送、拍一拍、记忆改写或管理员能力。

输出是结构化决定，不是长篇内心独白，不是完整回复文案：

~~~json
{
  "action": "reply",
  "topicId": "host-known-topic",
  "targetMessageIds": ["host-known-message"],
  "goal": "澄清这次配置疑问",
  "novelty": "补充刚确认的参数含义",
  "materialRefs": ["message:known-id"],
  "validUntil": "host-bounded-time",
  "initiativeProposal": null
}
~~~

动作集合及语义：

| 动作 | 意义 | 是否外发 |
| --- | --- | --- |
| reply | 回应一个或多个明确相关目标，合成一个交流回合 | 进入 Replyer，不保证必须发 |
| share | 主动分享有来源的新内容，目标是话题或会话，不伪造被回复消息 | 进入 Replyer，使用主动预算 |
| react | 适合一次表情/短反应的参与意图 | 进入受控表达路径，不强配文字 |
| listen | 本轮旁听，等真实新事件 | 0 |
| wait | 对方可能还在输入或材料即将补全 | 当前 0；宿主持有有限等待，不定时空跑 |
| close | 当前话题自然结束 | 当前 0；更新话题，不关闭整个群 |

目标决定允许一次有限 JSON 修复；再失败则明确结束本轮并审计，不进入“为了修结构不停生成”的循环。所有 ID、范围、期限和工具权限仍由宿主校验。

## 7. Replyer 与一个交流回合

Replyer 使用新构造的上下文，而不是继承 Planner 的全部工具历史、旧生命周期全文和故障叙述。输入包括人格原文、当前话题的真实消息、所选意图与目标、必要材料、近期自己的实际回复和相关记忆。

人格仍可以嘴欠、温柔、跳脱、认真，不要求每条都证明人设。平台不规定必须 2-3 条、必须问句结尾、必须表情或固定字数。技术解释可长，闲聊可短；主体性不靠故意答非所问实现。

生成输出先视为 ResponseDraft：可以是一条或几条文本、一个表情、工具辅助结果，也可以是无输出。send_message 等现有插件能力保留，但必须经统一宿主发送入口提交，不能从 Planner 直接执行。

一个 turnId 绑定同一表达目的。额度是上限，不是目标；文字与表情统一计入可见动作预算。明确系统命令走独立可审计 commandId，不能伪装社交意图绕过发送安全，#龙time 的图文来源验证保持不变。

Planner/Replyer 是逻辑职责，可使用同一模型。常规复杂群聊可各一次调用，工具场景允许有界追加轮次；固定系统命令可走不调用模型的快捷路径。前期不为了省一次调用而重新混合职责，也不为每条短消息配置一组高成本模型评审。

## 8. 生成期间的新消息与发送前有效性

Draft 保存 sceneRevision、topicVersion、targetMessageIds、coveredMessageIds、materialRevisions、turnId、intentId 和有效期。检查以“生成时已知什么”为基准，不以“目标必须永远是最后一条消息”为条件。

| 新变化 | 处理 |
| --- | --- |
| 同一问题补充关键条件、明确撤回、别人已充分回答 | 丢弃未发草稿或有限重规划 |
| 其他话题有人发消息 | 当前草稿可继续，不因群总版本变化取消 |
| 同一话题普通无关插句 | 更新软判断，不必机械取消 |
| 记忆被归档、纠正或来源失效 | 去掉失效材料，必要时重建 Draft |
| 已发出前半部分后情况变化 | 保留已确认效果，取消未发部分；不能整批重发 |
| 权限、运行模式、时间窗口改变 | 立即停止后续动作 |

最终 guard 在队列等待后、写出站意图前执行。已开始投递的请求可能无法撤回；一旦 unknown，进入现有人工核对流程，不声称 exactly-once。

每轮最多一次语义重规划作为初始建议；持续关键变化则等下一次稳定输入。不能在繁忙群无限取消，也不能为了保证发出去而发已知过时的内容。

去重分两层：宿主拦截同 turn/同投递的重复副作用；表达层结合近期同话题内容判断是否只是换词复述。相似度只作为信号，不能全局禁止“好”“谢谢”或合法重复回答不同问题。

## 9. 主动意图：保留兴趣，取消催场

### 9.1 允许的来源

- 人类互动中有未完成的共同话题或约定，且不把普通寒暄误认成任务。
- 工具新获取的公开资料，对已有共同兴趣有新的信息价值。
- 当前明确设定的兴趣和已验证共享话题形成的表达候选；不要求先有人下命令。

这比早先“所有意图必须引用本次人类消息”的草稿更完整：主动分享可以引用宿主记录的 external_observation 和兴趣来源，但它们不能作为人类偏好确认。模型的“我刚才说过”不是独立新来源。

### 9.2 生命周期

~~~text
proposed -> pending -> leased -> completed
                |        |----> cancelled / expired
                |        |----> held（结果未知或无法证明无副作用）
                +-------> cancelled / expired
~~~

意图保存具体 goal、sourceRefs、topicId/会话目标、dueAt、expiresAt、causalRootId、评估次数和投递标识。时间仅指定可评估机会，不保证会发言。冷场、刚刚发过言、没人回复、错误恢复、token 用完不构成新的意图。

无人回复的预算只因与该意图相关的人类接续或明确取消/过期而更新，不能因机器人又发一句或别人换话题而复位。逾期意图不能永久锁死以后有新来源的主动分享，也不能通过反复新建 ID 无限催同一件事。

到期但时机不合适时可放弃；确有未过期理由可对同一意图做有限延期，次数不清零。timer 触发不得递归新建同源意图。无意图、无新来源的普通 tick 为零模型调用。

可选探索只在管理员启用、存在兴趣来源、独立预算且无未回应意图时进行，使用只读工具形成新观察；它不是默认持续思考循环，也不按小时凑内容。本版支持显式配置的探索机会，不自动开启新增外部调用。

## 10. 四类记忆与两条反思路径

| 类型 | 示例 | 写入与读取规则 |
| --- | --- | --- |
| episode | 一次有趣的交流、暂时的感受、未确定的想法 | 可一次记录；区分谁说、谁经历、事实/推测/玩笑 |
| preference_candidate / adopted preference | 倾向先说结论、对共同话题的兴趣 | 候选和已采用分开；来源、范围、反证、TTL |
| initiative | 想分享刚查到的资料、稍后接一个未完话题 | 只在意图模块中执行；笔记不能创建执行权 |
| operational | 投递状态、禁言、重试、模型请求失败 | 由宿主持有，不进入普通聊天记忆召回 |

### 10.1 经历反思

单次互动或明确沉默可以留下有意义的经历，也可以什么都不记。允许角色视角原文，不强制写客观摘要，不新增二次润色模型。自己的真实行为可以记为经历，但不是用户认可的证明。

### 10.2 偏好学习

候选保存 claim、subject（谁的偏好）、scope、supportRefs、counterRefs、independentRoots、interactionIds、createdAt、lastObservedAt、expiresAt、status。用户偏好不能自动变成机器人偏好。

初始建议：稳定推断需要至少三次独立互动支持同一候选；这不是简单的三个 session 或三个任意消息。模型负责语义归纳及选择支撑原文，宿主验证来源独立性、作用域、当前性和不得自证，审核界面展示实际支撑与反证。不能靠手写中文关键词匹配证明语义蕴含。

明确用户纠正可以立即影响当前上下文，并撤销旧的错误表述；不必再等三次。全局人格变更、权限和调度规则由管理员控制，不从聊天学习。跨群候选不能拼接私聊原文；全局采用需要专门、可授权的抽象证据和审核。

人格可以形成自己的暂时观点和偏好候选，但不得用自己输出的回声作为新的独立支持。初期行为 trait 采用保持 review-only，这是长期行为的采用方式，不是对每条笔记或每次发言进行审核。

### 10.3 分离执行和校验

同一反思请求可以返回 notes、traitCandidates、capabilityGaps，但分别校验、提交和审计。一个 trait 不合格不能丢掉合法经历；一个普通笔记也不能借“system source”绕过记忆策略。旧事件资料可作经历参考，不补造 v3 字段使其变成合格偏好证据。

宿主持久累计窗口按原始互动来源组织，和模型输入缓存生命周期分开；只加载有界且同范围的证据。具体时间跨度可调，不能以增加上下文长度掩盖累计错误。

## 11. 统一 Context Builder 与记忆撤销

Planner 读取现场优先、记忆次之；Replyer 在参与意图确定后重新选材料。只读工具按需补充。所有内存入口使用同一授权、类型、版本、过期和隔离策略：自动召回、notebook_search、反思检索、人物记忆、交接和旧 transcript 的派生材料。

先判断资料是否可用于这个目的，再做向量或其他相关性排名。相似不等于可靠，更不等于当前指令。检索允许零命中，不按数量补满旧笔记。

历史正文只作为带来源的材料。记录“某人讨论网络重试”是合法技术经历；记录“以后发送失败就30分钟重试”是运行脚本。分类不能只靠 blacklist；需要字段来源、语义类别、宿主能力边界一起约束。高不确定旧材料可先隔离，不自动改写成另一份“正确笔记”。

MaterialRef 至少包含 kind、id、revision、scope、visibility、policyVersion。归档/纠正/权限变化提升对应材料 epoch；旧向量不可命中，缓存失效，在途生成发送前检查失效材料。social 不续用旧生命周期模型全文；切换模式时关闭旧执行上下文但保留审计，不删除历史聊天。

## 12. 持久化、接口与运维

建议模块：src/conversation/{state,opportunity,planner,replyer,context,intents,runtime}.js。文件数量由实现者按复杂度调整，职责边界不变。小模块可合并，但不能把全部逻辑重新塞进 Orchestrator。

持久数据最少包含 scenes/topics/message_links、interactions、intents/intent_events、turn_outcomes 和 candidate_evidence。允许复用宿主 SQLite 连接，由模块独占自己的表，不跨模块直接改别人的表；迁移加性、幂等，可在旧库副本验证。

公开内部契约：

| 接口 | 输入 / 输出要点 |
| --- | --- |
| Scene.observe / snapshot / assignTopic | 宿主事件 -> 场景、话题版本、互动 ID；语义归属需来源校验 |
| Planner.decide | Scene + Trigger + 有界只读能力 -> ParticipationDecision |
| Context.build | Decision + current material refs -> 两阶段各自的上下文 |
| Replyer.generate | Intent + 材料 -> ResponseDraft / no_output；不直接拿底层网络发送权 |
| Intent.propose / claimDue / resolve / cancel | 有来源提议 -> 持久状态；租约与投递事实关联 |
| Delivery.preflight / commit | Draft + current scene -> allow/replan/drop/hold，再委托 Sender |
| Memory.observe / retrieve / invalidate | 统一类型/范围/版本入口，模型不能自报权限 |
| Reflection.propose / Candidate.review | 经历与长期采用分开；人工审核不重新解释投递事实 |

管理端扩展现有会话和设置页面：模式、当前话题、回复对象、参与动作、材料来源、实际外发、未发原因、待办期限/取消、记忆隔离/归档预览与候选审核。不能展示原始隐藏推理；短 goal/novelty 是可审计意图，不要求长内心分析。

停用后不启动 worker、不创建新库、不调用模型；允许读取已有状态并取消既有待办。所有写操作需要现有管理鉴权、宿主账号和范围校验，GET 不因“查看”初始化库或改变队列。

## 13. 建议默认值和效果预算

下表是初始调参值，不是普遍最优值；应集中配置，并在页面说明单位和生效范围。

| 参数 | 建议起点 | 含义 |
| --- | --- | --- |
| 活跃话题上限 | 8 | 防止场景无限增长，不代表只记8个话题 |
| 近期现场消息 | 60，上限200 | 可按工具补读，不重复灌入全群历史 |
| Planner / Replyer 轮数 | 3 / 6 上限 | 不是必须用满；共享已有 Run deadline/token budget |
| 同一草稿语义重规划 | 1次 | 防止繁忙群无限取消 |
| 可见动作预算 | 普通闲聊默认最多3个 | 不强制发3条；技术长答不按短句拆分 |
| 主动发言冷却 | 30分钟 | 只是机会下限，不生成发言理由 |
| 同因果链未回应主动回合 | 1 | 有新独立来源可重新评估，不靠机器人自我发言复位 |
| 意图有效期 | 默认6小时，按事件有界调整 | 过时内容不再补发；管理员提醒不混入社交意图 |
| 偏好有限有效期 | 30天起点 | 过期不是删除；人工长期规则另行管理 |

同一模型可承担两个阶段，配置保留以后指定专用模型的空间但不在本版强制新增 provider 系统。所有调用按用途计账；成本不足时允许旁听/跳过主动，不重放旧台词。

## 14. 迁移、隔离与回退

1. 只读盘点当前配置、profile、Notebook、向量、交接、待办和版本；生产数字需要实施时重新取样。
2. 新策略先在临时旧库副本回放。对候选污染条目给出 id/revision/reason 的预览，包含合法技术记忆的反例。
3. 经授权进行一致性备份后，用带 expectedRevision/CAS 的归档操作处理明确污染，保留原文、历史和审计；不手改 SQLite、不凭关键词批量硬删。
4. 更新读策略与材料版本，使自动召回、工具读取、反思及在途上下文同步停止使用已失效内容。
5. 显式选择 social 模式；保留账号、人物卡、白名单、禁言与运行状态，不自动激活新外部调用。
6. 回退只切回原模式并取消新内核执行，不删除新表；未知投递保持 held，不能在回退后重新发一遍。

## 15. 决策自由度、未解决风险和实施纪律

固定契约：来源与投递事实归宿主；参与和表达分离；普通经历不受 trait 门槛挟持；无因催话取消；未知投递不重放；记忆不创建执行权；跨账号/私聊隔离；旧新上下文不能混用。

实现者可自主选择：模块拆分、SQL 索引、结构化输出编码、话题启发式、候选合并的有限语义辅助、UI 展示布局。模型轮次/预算阈值可以提出调整，但不能为了测试通过恢复 legacy 宽松资格、全盘静默或自动开启生产。

主要风险：话题误归属、Planner/Replyer 意图损失、额外延迟、过度拒答、依赖特定模型、记忆误隔离、持续未回应导致永久沉默。对应采取可纠正场景、有限重规划、反例回放和管理可见性，而不是继续堆黑名单。

本版不承诺“只要采用该架构就一定像人”。架构负责减少错误驱动，让模型有表达空间；最终应按人类可感知效果迭代，不能把没有逐字重复等同于自然对话。

## 16. 文档与实施状态

本设计优先于此前单纯 LSR 修补方案中的冲突项，尤其是“所有沉默禁止反思”“每条笔记需要用户确认”“主动性只能来自用户任务”等过度限制。历史 LSR 文档保留，不倒改验收历史。

2026-10-13 用户要求先落文档后开发，代码执行者已中断；随后明确授权将全部未完成代码与文档提交GitHub作为WIP保存点。该授权仅用于保全与交接，不能按本文自动继续开发、部署或清理线上。恢复前必须读取交接、核对 Git 与当前实现差异；状态模块的4个测试通过不代表完整内核通过。
