# qq-agent-plus：向量记忆与角色笔记功能修复开发规划

> 基线：`9069a4fcab93c4f3e8946fcc5318866ac3898fb3`  
> 仓库：`Velvetalon/qq-agent-plus`  
> 核对日期：2026-09-28  
> 用途：直接交给开发 Agent 执行。本文是实施计划，不是已修改、已部署或已通过测试的报告。

## 0. 交付目标与边界

**本版只把现有功能做成可用闭环，不再升级插件架构。**

最终应当发生的事情是：机器人按自己的角色视角留下笔记；正文立即可靠保存；后台独立生成向量；后续聊天或反思按权限找到相关笔记；服务异常时能够恢复；修改、归档后不会继续使用旧版本。

```text
真实聊天 → 有界证据 → 角色决定是否留笔记 → 正文提交
                                                ↓
                                   独立索引消费者 → 就绪向量
                                                ↓
                         新聊天 / 笔记搜索 / 后台反思 → 相关原文
```

### 0.1 已有实现应保留

- SQLite 的 Notebook 正文、版本和审计表。
- `sqlite-vec@0.1.9`、普通 BLOB 向量表、`vec_distance_cosine()` 查询。
- PluginManager、既有 ContextProvider、SessionObserver。
- `stay_silent`、消息 ack、Sender/Outbox、unknown 外发保护。
- 已实现的反思整体 deadline、租约余量、耗尽重试的过期作业终结。
- Learned Self 与 Base Persona 分离、版本检查和回滚。
- 新版角色笔记任务与共享 `notebook-policy.js`。

### 0.2 本版不做

不增加 Redis、独立向量数据库、本地 embedding 模型、通用队列平台、人格引擎、关系图谱、自动改人物卡、娱乐插件、自动私聊或自动开发插件。不再修补 Notebook 的自制中文分词和 n-gram 排名。

### 0.3 证据边界

本次重新确认远端 main 仍为上述提交。已确认问题来自固定版本源码和上一轮专项复查；上一轮执行的是摘录逻辑与内存 SQLite 的局部探针，**不是完整生产装配、真实 embedding、真实角色行为或线上验证**。

开发 Agent 必须在自己的实际工作区重新记录 HEAD 并执行测试。若 HEAD 已更新，先识别已经修复的部分，不得把旧问题硬套回新代码。本文提出的新接口、字段和状态均标为实施契约，不应假设已经存在。

## 2. F1：宿主持有 Embedding 凭据，插件只获得调用能力

### 2.1 当前问题

正式路径是 `PluginManager.startAll()` → `snapshotPluginConfig(config)` → 插件 `start()` → 从脱敏配置创建 `EmbeddingClient`。`apiKey` 被替换成 `[redacted]`，客户端仍按 `config.apiKey` 构造 Bearer header。[S1][S2][S3][S4]

`apiKeyRef` 被读取但未解析；`startAll()` 又跳过已 running 实例，因此后填配置或更换模型时，旧客户端可能继续存在。不能通过删掉脱敏来修这个问题。

### 2.2 修复方式

**由 `src/console/app.js` 这个真实装配入口使用私有配置创建客户端。** Notebook、Reflection 和 Retrieval 不再从脱敏配置自行创建带密钥的客户端。

可以增加一个小的宿主 helper，但不要做通用服务容器。宿主向插件提供只暴露以下能力的 facade：

```text
读取非敏感状态 / profile 元数据
按宿主校验过的来源编码笔记
按宿主校验过的当前聊天编码查询
```

实施要求：

1. 不直接将含公开 `.config.apiKey` 属性的原始 EmbeddingClient 塞给插件；用闭包/受限对象隔离密钥与任意 HTTP 能力。
2. 调用方不能指定任意 endpoint、Authorization、账号或跳过授权；这些由宿主绑定。
3. `apiKeyRef` 只解析现有已授权凭据来源；若没有该能力，保存配置时明确拒绝“不支持的引用”，不得默默当成可用。
4. `[redacted]`、空引用等占位值不能当成可用凭据。无鉴权服务只能通过明确配置使用，不把缺 key 自动解释为匿名模式。
5. `provider/model/dimension/profileId` 取自同一份规范化宿主配置。不要让 VectorMemory 用新配置算 profileId，却用旧客户端发请求。

### 2.3 配置热更新契约

每次有效变更形成一个不可变运行快照，至少绑定客户端、模型/维度/profileId、授权策略和运行代次。每个索引或查询操作在开始时固定快照，不在 await 返回后从可变 `this.config` 重新决定结果归属。

| 配置变化 | 需要的处理 |
|---|---|
| 仅保存无关设置 | 不重启客户端，不使在途任务失效 |
| 补填 endpoint/model/key | 已运行插件获得新能力；不要求重启整个 bot |
| 轮换 key，模型等不变 | 更新客户端，解除对应鉴权暂停；不重建已有有效向量 |
| 更改模型、维度、query/document 编码前缀 | 新 profile 隔离；旧向量不参与新 profile 的查询 |
| 收回外发授权或禁用 | 停止新请求，尽力取消在途请求，禁止晚到结果写入当前索引 |
| 保存非法配置 | 返回明确错误；当前可工作的配置不得被半更新状态破坏 |

没有完整的 profile 热切换能力时，允许只对这三个自我迭代插件做受控 stop/start；必须实际执行生命周期并保持数据，不能“改表单后其实要重启”却不告诉用户。

请求已经发往远端的文本不能被撤回。取消保证的是停止后续行为和拒绝不适用的晚到结果，不得承诺抹去提供商已收到的内容。

### 2.4 开关各管一件事

不要因为 embedding 配置目前放在 `retrieval.embedding` 下，就继续用自动召回开关决定是否创建所有客户端。

| 条件 | 应运行的行为 |
|---|---|
| 总开关关闭 | 不启动自主写入、索引或反思；管理端按原权限查看已有数据 |
| 总开关开启、embedding 未配置/未授权 | 可记笔记；无远端向量请求；没有语义召回，状态明确 |
| embedding 合法且已授权，自动召回关闭 | 后台处理已授权的新索引；手动语义搜索可用；不自动向每次聊天注入笔记 |
| 自动召回开启，embedding 不可用 | 不伪装 ready，不退回自制中文排名；普通聊天继续 |
| 反思关闭，Notebook/embedding 仍开启 | 仍可手动记笔记和后台索引；不调用反思模型 |
| 反思开启、自动召回关闭、embedding 可用 | 反思可以按本任务授权读取相关笔记；聊天自动注入仍关闭 |

本表是本版需要统一的目标语义。旧数据不自动触发付费补建，按 F3 的授权恢复规则执行；保存配置不覆盖用户显式关闭的选择。

### 2.5 应有表现与验收

- 用户先开 Notebook，后填写合法 embedding 配置，当前进程开始处理之后的已授权索引任务。
- 从真实 `createApp → PluginManager → 插件` 路径，假 HTTP 服务收到测试用真实 key；插件配置、模型请求、普通日志中没有该 key。
- 切模型期间旧请求返回，不得用新 profileId 保存旧模型向量。
- 禁止直接注入 fakeEmbeddingClient 替代这项装配验收；只在最外层 HTTP 边界替换远端服务。

## 3. F2：让外发授权真正控制 HTTP 请求

### 3.1 当前问题

`EmbeddingClient` 有 `authorizeNote()` / `authorizeQuery()`，但 VectorMemory 直接调用编码方法，编码方法本身也没有执行授权。[S4][S5]

另外，当前 `allowQuery = allowQuery===true || allowPrivate===true` 会让显式 `allowQuery:false` 被另一开关覆盖。需要修正显式 false 的优先级，而不是继续依赖隐含联动。

### 3.2 修复方式

授权在 F1 的宿主能力边界实施。保留现有字段，不为此设计权限 DSL。

- 笔记外发使用数据库中的真实 account/scope/chat 来源校验，不信任模型参数中自报的来源。
- 查询外发使用宿主 RunContext，携带真实账号和当前 chat；后台反思按其作业来源绑定。
- `allowQuery:false` 必须阻止查询 HTTP；不能被 `allowPrivate:true` 绕开。
- 为兼容旧逻辑，`allowPrivate` 暂继续覆盖所有 `scope=chat` 的会话来源笔记，而不只是真正的 QQ 私聊。控制台说明其实际含义，不在这轮悄悄缩小保护范围。
- 字段缺失的兼容默认值集中定义一次；明确关闭优先。不要在不同入口自行补默认。
- 授权拒绝返回 `external-disallowed` 一类明确原因，不假装是 `no-matches`，不将其当网络错误频繁重试。
- 批量 document 接口若保留，只能接收逐条通过来源校验的输入；不可成为绕开单条笔记授权的后门。
- 读取缓存也需遵守当前访问范围。撤销策略后不能用旧缓存恢复被禁止的内容。

SQL scope 保护“哪些群能读到哪些笔记”；此处授权保护“哪些文本允许送到 embedding 提供商”。两者必须同时存在。

### 3.3 应有表现与验收

| 操作 | 预期 |
|---|---|
| 禁止会话笔记外发，写入 chat 笔记 | 正文正常保存；无 document HTTP；状态显示受策略阻止 |
| `allowPrivate=true, allowQuery=false` | 允许的索引可继续；查询 HTTP 次数为 0 |
| 修改配置重新授权 | 符合恢复策略的任务可继续，无需修改正文骗系统重建 |
| 反思尝试检索别群私聊 | 被范围限制拒绝，不能拿到正文，也不能以该正文请求 embedding |

测试必须断言假 HTTP 服务的调用次数为 0，而不是仅检查 `authorize*()` 的返回值。

## 4. F3：独立索引消费者、有限重试与恢复

### 4.1 当前问题

`NotebookStore.semanticSearch()` 会先 `await processEmbeddingQueue()`；积压笔记依次生成向量，占用聊天召回时间。任何异常都把任务标为 failed，之后只领取 pending，因此一次取消或网络问题可能使该版本永久无索引。[S5][S6]

当前反思和 Notebook 各有连接，也可以触达索引消费入口；必须明确唯一消费者归属，避免并发处理同一任务。

### 4.2 写入路径：正文先可靠保存

保留现有正文库，所有写入入口统一通过 NotebookStore：聊天工具、反思操作、管理端编辑/归档。

```text
正文写入 / 版本更新
    → 同事务记下该版本需要索引的持久意图
    → 返回正文保存结果
    → 后台消费者在之后处理
```

“与向量服务解耦”不是“把索引任务写失败吞掉”。正常数据库下，成功正文提交应伴随可恢复的索引意图。向量扩展未加载、凭据缺失或远端离线不能妨碍正文提交；派生表的基础 DDL 和任务写入不得依赖扩展函数。

若本地索引意图确实写失败，要返回/记录独立的 `index-enqueue-failed` 状态，并允许管理端补建。不得用空 catch 宣称全部成功。数据库本身无法可靠提交时则按真实存储错误处理，不假装已保存正文。

模型可见结果区分 `saved` 和 `indexStatus`。`saved:true,indexStatus:pending` 表示正文已保存，不代表现在就能语义搜到。

### 4.3 索引消费者归属

在现有 Self-Evolution 生命周期中增加一个小型消费者，默认并发 1；由 Notebook 插件或其宿主专用 helper 唯一拥有。

- Notebook 活着且索引配置有效时启动；停止时取消自己的任务并释放连接。
- Reflection 只提交笔记变化和调用检索，不再自行 drain 索引队列。
- 自动召回和手动搜索不领取、不生成、不重建任何笔记向量。
- 消费者使用自己的取消信号。某个聊天 Run 超时或用户取消查询，不影响正在生成的笔记索引。
- 无任务时有界轮询或等待写入通知，不忙等；重启后继续处理已允许且未完成的持久任务。
- HTTP 等待期间不持有 SQLite 写事务。
- 索引并发限制只管索引；查询不能排在整批文档任务后面等 FIFO 清空。需要共享供应商限流时，查询可有独立的小预算或优先级，不引入另一套调度平台。

### 4.4 最小持久任务契约

沿用 `notebook_embedding_jobs`，必要时迁移字段/约束；不另建通用任务系统。任务至少能表达：

```text
accountId, noteId, revision, inputHash, profileId
状态、attempts、maxAttempts、availableAt、lastErrorCode
领取所有者/代次、leaseToken、leaseExpiresAt
阻止原因（缺配置 / 禁止外发 / 鉴权暂停等）
```

可以保留现有状态并增加 lease/blocked 字段，也可以小范围重建 CHECK 约束；实施前写清实际状态映射，并测试旧库迁移。不把文中的逻辑状态名直接硬塞进不允许该值的旧 CHECK 约束。

必须满足以下不变量：

1. 领取是数据库原子操作。同一任务同一时刻只有一个有效 leaseToken。
2. task 的 profileId、revision、inputHash 与请求使用的不可变快照一致。
3. 远端返回后，在短提交事务中再次核对正文仍存在、active、revision/hash 未变、授权仍有效、leaseToken 匹配。
4. 笔记已编辑/归档/删除、模型 profile 已切换或任务已重领，旧结果不得写入当前 ready 索引。
5. 过期任务恢复也受最大尝试次数约束。达到上限进入终态，不继续占据队首。
6. 无代价的禁用检查/轮询不增加调用次数。真正开始的远端尝试要记账，即使取消或超时，不能反复清零规避预算。
7. 单进程 single-flight 只是优化，不替代数据库领取约束；测试中用两个连接验证无重复领取。

### 4.5 错误分类与恢复表现

| 情况 | 状态处理 | 自动恢复方式 |
|---|---|---|
| 网络中断、连接超时、远端 5xx | 延迟重试 | 建议总共最多 3 次，指数退避；阈值可配 |
| HTTP 429 | 延迟且限速 | 尊重可用的 Retry-After；无则退避，禁止紧密重试 |
| HTTP 401/403 | 对当前客户端/profile 暂停 | 修正凭据后恢复选定未完成任务，不轮询轰炸远端 |
| 插件停用/进程退出 | 停止领取，释放或等待 lease 恢复 | 重启且重新允许后继续，不标成内容永久失败 |
| 当前聊天取消 | 不影响索引消费者 | 只结束该查询 |
| 返回维度不符、NaN/零向量、协议不兼容 | 当前 profile 报配置/响应错误 | 不无限重试同一配置；显示错误并等待修复/显式重试 |
| 笔记已变更或撤销 | obsolete | 新版本走新任务，旧结果丢弃 |
| 次数/每日预算耗尽 | 明确终态或暂停到恢复时刻 | 不永久占队首，不立即重复领取 |

取消不能把后续恢复能力抹掉，但已经发生的远端尝试仍计入预算。恢复失败任务是有边界的操作，不是每次进程重启就重置尝试次数。

### 4.6 旧笔记与模型变更后的补建

提供现有管理页下的“预览补建 → 确认提交”入口。只处理当前管理员被授权的账号/范围，按游标或上限分批。

- 补建读取当前正文版本，创建派生任务，不改正文、创建时间、笔记 revision 或角色口吻。
- 旧的无 profile 任务与失败任务有明确迁移分类，不能无条件全量重新发往远端。
- 用户明确启用后新产生的允许笔记，自动索引；启用前遗留笔记、模型更换后的历史笔记，先显示覆盖缺口，通过补建入口授权。
- 同 profile 修正 key 后，可以恢复该 profile 已授权的鉴权暂停任务，不强制重建所有 ready 向量。
- 同一补建请求/游标重复提交不重复创建相同版本任务。
- 页面显示预计条数/输入字符规模、已就绪/待处理/失败/受策略阻止。没有供应商价格数据时不编造费用金额。

### 4.7 应有表现与验收

1. 假 HTTP 服务挂住 document 请求时，`notebook_append` 仍在远端响应前返回正文保存成功。
2. 不再发任何聊天消息，后台也会把允许的新任务处理到 ready。
3. 查询时有 8 条积压，抓取请求证明查询本身只可能产生 query embedding，不偷偷产生 document embedding。
4. 首次网络失败、第二次成功，笔记最终可搜到，不需要再次编辑正文。
5. 两个消费者争抢同一任务，只有一次有效提交；旧 lease 返回不覆盖新状态。
6. 在途编辑/归档/切模型、重启和终止恢复均有用例。

## 5. F4：三个调用入口共用纯查询路径

### 5.1 当前问题

自动召回、手动 `notebook_search` 和 Reflection 已经能调用向量查询，但查询夹带索引消费；semantic 结果使用 noteId/snippet，部分调用方仍按 id/content/scope 读取，存在适配不完整风险。手动工具的 semantic 分支还未完整透传 tags 和取消信号。[S5][S6][S7]

这些是需要封口的接口问题，不是再新增一种检索算法。

### 5.2 统一行为

`semanticSearch()` 只做：校验授权 → 确认有可查询的 ready 索引 → 向量化查询 → SQL 过滤和距离排序 → 返回当前原文摘录。

- 不生成文档向量，不 drain 队列，不因一次搜索触发历史付费补建。
- 没有任何可见 ready 候选时，直接返回 `index-not-ready`，避免先花钱编码查询再发现空库。
- 自动召回保持约 5 秒的独立预算；HTTP 超时应被当前调用的更短剩余预算约束。后台索引使用独立的更长请求预算。
- HTTP/授权/配置失败返回原因。自动聊天正常继续，不强迫机器人对群友播报“召回故障”。
- 不静默退回原来的自制分词排名。配置缺失时是明确无语义召回；精确 ID 读取与普通列表仍可用。
- 不要求填满 topK。阈值作用于当前 profile，可配并用选定模型校准；现有 `distance<1` 不能被宣传为经过验证的相关性标准。

### 5.3 SQL 与结果字段

继续在 SQL 的候选阶段限定：当前账号、允许 scope、active、当前正文 revision、当前 profile。授权和过滤不能移到 topK 之后。tags 是完整标签匹配，不是任意子串命中；不得扩大 scope。

定义一个共享 NoteHit（字段名称可沿用当前兼容别名，但全链一致）：

```json
{
  "noteId": "真实笔记ID",
  "revision": 3,
  "scope": "chat",
  "chatKey": "group:12345",
  "tags": ["经历"],
  "snippet": "数据库中的原文摘录",
  "isTruncated": true,
  "distance": 0.2,
  "rankingSource": "sqlite-vec"
}
```

上述数值仅为格式示例，不是推荐距离阈值。允许兼容 `id`/`content`，但不能把缺失字段默默变成空串；尤其不能把摘录伪装成完整 content。

精确读取可对现有 `notebook_search` 增加 `noteId` 精确模式，或复用实际已有工具。无需另增一堆工具：模型获得真实 noteId 后，能在授权内读取完整当前正文与 revision 即可。此路径不调用 embedding。

### 5.4 三个使用者的表现

| 入口 | 应有表现 |
|---|---|
| 自动聊天 ContextProvider | 只将本次真正选中的当前笔记原文加入动态上下文，零命中时不填充无关内容 |
| 手动 notebook_search | 返回同一 NoteHit 契约，透传 tags/scope/取消；注明索引未就绪和精确读取方式 |
| Reflection 相关旧笔记 | 使用同一语义范围与当前版本；索引不可用可以无相关笔记反思，并记录原因，不把“最近八条”假装成相似结果 |

语义摘录用于帮助判断“有没有相关旧事”。要整体修改一条笔记时，必须读完整正文，见 F6。

### 5.5 应有表现与验收

- “拍照片/摄影”类真实语义测试在获得服务凭据后进行；假向量只能验证距离排序和管线，不能宣称证明中文理解。
- 关键词缺失、前一条消息很长，不再受自制 n-gram 额度影响。
- 长输入按 embedding 的实际长度限制做有界选材，保留当前目标消息；不是把全群历史直接送去编码，也不是重新建设中文分词器。
- 无关话题、别群私聊、归档或旧 revision 不能进入最终模型请求。
- 编辑/归档后，旧向量和旧生命周期中的派生注入都失效；保留真实聊天原始历史，不删除原始消息。

## 6. F5：证据预算在入队之前闭环

### 6.1 当前问题

聚合载荷中重复正文已删除，不能再次把旧 bug 原样返工。当前剩余问题是：归一化和聚合结果大于 12,000 字符时仍直接抛错，没有按总大小裁剪。来源 ID、引用集合和观察元数据同样占空间。[S8]

上一轮 15/20 条、单条 240 字符的合成样本仍可超限；这是 fixture 结果，不是“第十五条必炸”的全局阈值。

### 6.2 修复方式

增加一个小的 evidence-budget helper，贯通以下位置，不另建消息仓库：

```text
宿主选择有限源消息和确认回复
 → 完成事件构造与持久化
 → normalizeCompletionObservation 后的持久化预算
 → aggregateObservations 后的作业预算
 → reflectionPrompt 最终请求预算
```

实施规则：

1. 正文在单份聚合 payload 中仍只保存一处；observations 只带来源和逐次执行质量。
2. 计量统一为现有 `JSON.stringify(value).length` 字符口径；最终 prompt 也按同一单位统计，不能混用 UTF-8 字节或 token。
3. 对最终对象裁剪、重新序列化、检查；不要仅做“20 条 × 每条 240 字”估算。
4. 先合并重复元数据/来源，再保留最新关键互动，确保有用户消息与已确认机器人回复；不要先把用户消息放满 20 条再裁掉所有回复。
5. 继续超限时缩短旧片段、低相关旧笔记和过长单项，标记 truncated；不把 JSON 字符串直接截断，不切坏 Unicode 字符。
6. 删除消息正文时同步删除其作为聊天事实可引用的 evidenceRef；运行结果的引用单独保留。模型不能引用它实际没看到的完整原话。
7. 裁剪审计也需要预算：省略条数、少量省略 ID、原始/保留字符数即可，不再把被省略的全部原文复制进审计。
8. 合法长材料能缩减为有意义输入；连最小上下文都放不下时，明确记为 evidence 不足/noop 并结束该观察，不反复重投同一个超大输入。
9. 不能为凑预算删除故障/来源信息并把不可靠观察改成可靠。来源、scope 与当前有效证据仍受校验。

### 6.3 反思 deadline 与重试：保留已有修复，只补跨服务验收

当前整体任务 deadline、作业 lease 余量和耗尽尝试作业终结已存在。本版不重写这套机制。

但 F4 引入远端查询后必须验证：相关笔记检索遵守自己的时间预算，不消耗全部反思窗口；任务取消后晚到结果不提交；卡住或失败的作业有限结束，下一条正常作业继续。

若当前实现只声明 `retrievalTimeoutMs` 却没有真正约束等待，应在实际 await 边界使用子 deadline。不是单纯把所有 timeout 再加大一倍。

### 6.4 应有表现与验收

- 15/20 条人工长消息经过真实完成事件、SQLite、observer、job 后产生合规作业，不在入队前抛同一类超限异常。
- 最终发给反思模型的请求确实含保留下来的关键对话和确认回复，且整体不超过配置预算。
- 超大不可缩减元数据有明确终态，不影响聊天正常 ack，不在每次后台轮询重新报同一个错。
- 保留 API/tool 正常讨论与正常主动沉默不被误判技术故障的回归。

## 7. F6：保留角色笔记，而不是重新做“有口癖的摘要”

### 7.1 当前状态

`notebook-policy.js` 和 `reflectionPrompt()` 已经改成角色给未来自己留话，原有“只有长期事实才能记”的硬关键词门槛也已取消。不要重新把人物卡写长，不把已实现部分包装成待开发大模块。[S9]

未验证的是实际角色选择和语气；还需要统一工具描述、原文摘录适配和安全更新行为。

### 7.2 修复与保留要求

- 共享当前管理员人物设定、关系与已采用偏好；后台切换为笔记任务，不执行群聊发言义务、极短回复和 send_message 规则。
- 同一次反思中决定“注意什么、是否值得记、怎么看、怎么写”，不新增第二次润色调用。
- `notebook_append` 的描述与共享笔记规则一致，允许经历、暂时印象、疑问、未完成念头，不继续只引导“用户事实/长期偏好”。
- 事实、他人说法、角色暂时判断和计划要分清；不能把群友的爱好自动写成自己的爱好，不能伪造自己参加过现实事件。
- 不强迫每轮写笔记、毒舌、提妈妈、提 AI 或提出 trait；空操作是正常结果。
- 旧笔记是参考，不是格式模板。不因旧笔记风格朴素就自动批量重写，不让角色不断模仿自己以前的口头禅。
- 正文保存生成结果，向量直接编码该正文/现有标签；不在后台另生成一份客观摘要取代角色原文。

### 7.3 新建、纠正和归档的实际行为

| 场景 | 应有表现 |
|---|---|
| 一次有趣但不“重大”的互动 | 允许留下具体经历；是否记录仍由角色判断 |
| 普通寒暄、无新内容 | 可以不记录，不制造“今日成长” |
| 新证据推翻旧印象 | 找到旧笔记，读取当前完整正文与 revision，修改或归档 |
| 只检索到部分摘录 | 可以用来理解上下文；不能据此整体覆盖未知原文 |
| 想继续做某事 | 可以记为念头；不等于已经创建提醒、私聊计划或获得权限 |
| 写下暂时不快 | 不直接升级为长期性格，不据一次沉默形成“讨厌此人” |

反思更新旧笔记时，宿主先按候选 noteId 取少量完整当前正文放入预算；放不下的条目标记不可整体更新，只允许保持不变或读取后另一次处理。不能靠提高 expectedRevision 绕过内容不完整。

每次更新沿用 CAS；冲突后重新读取，不盲重试旧覆盖。后台和聊天工具都要遵守相同规则。

### 7.4 应有表现与验收

工程测试证明：角色模式规则和当前人物资料进入实际反思请求；生成的正文原样进入 Notebook；之后召回仍是这份原文；更新走真实 noteId/revision，不覆盖未读部分。

行为测试使用真实模型和允许的测试群材料，观察选材和口吻是否有上下文依据，是否能普通地表达、不记录或改口。不得以“出现了妈妈/脏话/第一人称”作为人格通过条件；不得把示例台词写进产品提示词后再用同一句当期望输出。

没有真实模型凭据时明确 `LIVE_NOT_RUN`，不把 fake reflector 的固定文本当成性格模拟已经成功。

## 8. F7：控制台能解释状态，旧数据有恢复入口

### 8.1 当前问题

当前部分状态根据配置和实例存在就报告可用；向量状态统计主要读取 embeddings，未完整体现 jobs 的失败/积压。它们无法回答“为什么笔记在，模型却想不起来”。[S5][S10]

### 8.2 管理端最小状态表

复用现有页面，不新增大仪表盘。

| 显示项 | 必须来自什么 |
|---|---|
| enabled / effective / running | 真实配置及生命周期状态，三个含义分开 |
| embedding 可用性 | 扩展加载、客户端配置、授权、最后实际成功/错误；不能仅因 key 非空就说鉴权成功 |
| 当前 profile 与覆盖率 | 当前账号、当前 profile、active/current revision 的实际有效向量 |
| pending / retrying / blocked / failed | 真实索引 jobs，不用 embeddings 表的计数冒充 |
| 最近一次召回 | 实际 query 状态、命中数、最终注入数、版本、耗时、降级原因 |
| 最近一次反思 | 有界输入的材料计数、裁剪信息、真实应用/拒绝/noop 数量与版本变化 |
| 恢复入口 | 重试已选任务、补建预览/确认、配置修复；不能只显示红色错误却无操作入口 |

普通日志只记录标识、计数、错误码；敏感正文和完整输入仅在已认证管理端按既有权限查看。密钥永不出现在状态、URL、错误消息或审计里。

`ready` 不等于所有笔记已经索引；应同时显示可用性与覆盖。部分 ready 可以正常召回，剩余 pending/failed 单独显示。

### 8.3 升级和回退

- 保留原有安装目录、数据目录、Node/runtime 与 systemd 用户服务；读取 `AGENTS.md` 和实际运维文档，不从源码目录误执行部署管理命令。
- 使用项目已有一致性备份方式保存 SQLite，注意 WAL；不能把运行中的单个主库文件随意复制后宣称备份完整。
- 迁移在临时旧库 fixture 验证：旧正文/版本可读、派生 jobs 可分类、重复启动幂等。
- 旧 failed 索引任务按错误类型提供恢复，不擅自将全部改成 pending。历史补建先预览授权。
- 向量加载失败不影响普通聊天与正文读写；关闭检索或反思只停对应行为，保留数据。
- 回退优先关闭这轮功能或切回兼容代码版本；新字段不破坏旧数据读取，不自动删除原文和历史。
- 发布前用服务实际 Node 执行已有 sqlite-vec smoke，记录平台/架构/扩展版本。不要用开发机安装成功替代目标部署验证。

### 11.1 正式装配测试方法

1. 使用临时 DATA_DIR 和测试凭据，经真实配置/管理入口启用。
2. `createApp()` 或它在不改变生产接线前提下抽出的组合函数必须参与；不能直接 `new NotebookStore({fakeClient})` 替代 T01/T02。
3. 在本地 HTTP 假服务上记录请求 endpoint、测试 header、model、输入类型、调用次数和响应时机。
4. 用测试管理员真实工具路径写笔记，不先手动 `processEmbeddingQueue()` 再称后台功能通过。
5. 等待真实后台消费者推进；新 Run 经真实 ContextProvider 把笔记加入最终 LLM 请求。
6. 较长聊天经完成事件入库、observer、反思输入构造后抵达 LLM 边界；提供合法角色笔记操作并验证真实采用。
7. 同一条笔记在更正/归档之后，续接生命周期和新生命周期都不再注入旧派生版本。

### 11.2 工程通过和行为通过分开

- 工程通过：假 HTTP 返回控制向量/提案，真实代码完成鉴权、索引、查询、保存、采用和撤销。
- 语义通过：实际选定 embedding 模型能在允许的测试语料中区分相关/无关主题；报告数据集和阈值，不推广成所有话题必定正确。
- 人物表现通过：真实角色模型会自主选材、自然表达、适时不记和修正；不以固定台词命中作为标准。

没有真实凭据时后两项写 `LIVE_NOT_RUN`，工程结果仍可交付。不能假装已做线上行为验证。
